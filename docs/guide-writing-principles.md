## 1. 문서의 목적과 적용 범위

이 문서는 flashcards 홈페이지에 있는 ‘AI 직원 만드는 방법’ 카드들의 상세 페이지를 작성하고 수정할 때 사용하는 공통 기준이다. 사람이 읽기 편하고, 다른 대화의 AI도 같은 기준으로 글을 만들 수 있게 작성했다.

기준은 2026-11-23~24 ‘Thread 마케터 만들기’ 상세 페이지를 수정하면서 사용자가 직접 정한 방향과 현재 본문에서 재사용할 수 있는 구성이다. 이 문서의 목적은 수정 이력을 나열하는 것이 아니라, 다음 상세 페이지를 만들 때 같은 문제를 반복하지 않도록 하는 것이다.

마케터뿐 아니라 디자이너·PM 등 다른 업무 카드에도 적용한다. Threads 게시물, Notion, 게시 후 24시간, 게시물 10개라는 예시는 해당 사례의 선택이다. 다른 업무에서는 결과물·도구·성과 확인 시점을 그 업무에 맞게 바꾼다. Step은 최대 7개로 구성한다. 모든 글을 반드시 7개로 채울 필요는 없다.

이 문서는 상세 페이지의 글쓰기 기준이다. 제품 범위와 화면 정책은 [PRD](prd.md), 단어장 뜻 작성은 [용어 뜻 작성 가이드](term-definition-guide.md), 공통 작업·문서 규칙은 [공통 가이드](../../.claude/common/README.md)를 따른다.

## 2. 독자와 글의 목표

독자는 업무 자동화를 처음 시도하는 사람이다. 관련 용어를 모르고, 작업 폴더·참고 자료·가이드·스킬·도구 연결도 준비되어 있지 않을 수 있다. 해당 업무의 기존 결과물이나 성과 기록조차 없을 수 있다.

글을 읽은 독자가 ‘어떤 기술이 있는지’만 이해하는 데서 끝나지 않고, 지금 AI에게 무엇을 요청할지 알고 실제 업무를 맡기는 단계까지 따라갈 수 있어야 한다.

핵심 방향은 **사람이 본인의 목표와 판단을 알려주고, AI가 정리·준비·실행·기록을 맡으며, 부족한 정보와 사람이 해야 할 조작을 하나씩 안내하는 것**이다. 독자가 먼저 자동화 전문가가 되어야 따라갈 수 있는 글을 쓰지 않는다.

<a id="section-3"></a>

## 3. 핵심 작성 원칙

### 3-1. 사람이 미리 만들어야 할 일을 줄인다

‘문서·양식·폴더·표를 먼저 만들고 Codex에게 전달한다’보다 ‘Codex에게 만들라고 요청하고 필요한 정보에 답한다’를 기본 순서로 삼는다. 계정 로그인, 본인의 선호 결정, AI가 접근할 수 없는 화면 확인 등 사람이 직접 해야 하는 일은 남긴다.

| 피할 안내 | 권장 안내 |
| --- | --- |
| 성과 기록용 스프레드시트를 만들고 열을 준비한다. | 목표에 맞는 기록 양식을 Codex에게 만들라고 한다. |
| 필요한 연결 도구를 알아보고 설정한다. | 현재 연결을 확인하고, 내가 해야 할 설정만 하나씩 알려달라고 한다. |
| 참고 파일을 정해진 폴더로 분류한 뒤 요청한다. | 어떤 자료를 보내야 하는지 물어보고, 자료 정리와 저장은 Codex에게 맡긴다. |

### 3-2. 사람이 할 판단은 사람이 한다

어떤 업무를 자동화할지, 원하는 결과가 무엇인지, 초안이 마음에 드는지 등 본인의 판단은 사람이 한다. 간단한 업무 선택까지 반드시 AI의 추천과 승인을 거치게 만들지 않는다. 선택에 도움이 필요할 때는 질문이나 예시를 요청할 수 있게 한다.

AI가 한 정리 작업을 독자가 매번 파일을 열어 검사하도록 요구하지 않는다. 독자의 검토는 실제 방향·내용·결과물에 필요한 곳에 둔다.

### 3-3. AI는 알고 있는 것을 요약하고 모르는 것을 묻는다

‘이미 아는 것과 부족한 것을 구분해줘’로 끝내지 않는다. 기존 대화·문서를 먼저 참고해 파악한 내용을 요약하고, 추가로 필요한 것은 사용자에게 질문하도록 한다. 앞 단계에서 정한 목표를 뒤 단계에서 이유 없이 다시 처음부터 묻지 않는다.

### 3-4. 설명은 간결하게, 실제 과정은 구체적으로

독자에게 무엇을 해야 하는지 알려주는 안내는 짧고 직접적으로 쓴다. 업무를 수행하며 무엇을 했는지 AI에게 전달하는 예시는 구체적으로 쓴다. ‘짧게 쓰라’는 이유로 판단 이유와 막힌 상황까지 생략하지 않는다.

### 3-5. 처음 등장하는 위치에서 용어를 설명한다

워크플로우·가이드·스킬·하네스 등은 처음 필요한 곳에서 쉬운 말로 설명한다. 정의가 뒤에 나오는데 앞 단계에서 이미 전문 용어를 사용하지 않았는지 확인한다. 정의 이전에는 ‘업무 단계’처럼 익숙한 표현을 사용할 수 있다.

### 3-6. 준비된 사람과 준비되지 않은 사람 모두 따라갈 수 있게 한다

기존 작업물이 있는 사람만 대상으로 글을 쓰지 않는다. 없거나 적은 경우, 성과 수치를 모르는 경우, 도구를 연결할 수 없는 경우에도 다음 행동이 있어야 한다. 필요한 차이는 해당 단계에서 나누고, 본인의 상황에 맞는 경로를 선택하게 한다.

### 3-7. 지금 단계의 일만 한다

양식 만들기에서는 빈 양식과 항목을 정한다. 실제 성과를 수집하고 기록하는 일은 실행 이후로 모은다. 업무 기록을 배우는 초기 실습에서 성과 전달을 다룰 수는 있지만, 이후 자동 운영과 목적이 다르다는 흐름을 유지한다.

## 4. 전체 글의 흐름과 단계 구성

### Step은 최대 7개로 묶기

최상위 Step은 7개를 넘기지 않는다. 비슷한 목적의 일은 한 Step으로 묶고 내부 소제목으로 나눈다. 준비할 일이 여러 개라고 각각 독립된 Step으로 만들지 않는다. 이미 내용이 많은 단계에 무리하게 더 합치지 말고, 합친 뒤에도 독자가 한 단계의 목적을 이해할 수 있어야 한다.

현재 Threads 글은 기존 ‘작업 폴더 연결하기’와 ‘업무 목록 작성하기’를 ‘Step 1. 준비사항’으로, ‘업무 가이드 만들기’와 ‘성과를 기록할 양식 만들기’를 ‘Step 4. 업무 가이드, 기록 양식 만들기’로 묶어 9개에서 7개로 줄였다. 계정·앱 준비 안내도 Step 1 안에 포함한다. 단계를 합칠 때 본문·소제목 번호·목차·프롬프트의 단계 참조·페이지 소개의 단계 수를 함께 수정한다.

다음은 현재 Threads 글에서 추출한 기본 흐름이다. 업무에 따라 합치거나 나누되, 앞 단계의 결과가 다음 단계의 재료가 되도록 한다.

| 순서 | 독자가 하는 일 | AI가 만드는 것·준비하는 것 |
| --- | --- | --- |
| 준비 | 계정과 작업 환경을 준비한다. | 필요한 준비와 사람이 할 설정을 안내한다. |
| 작업 연결 | 작업 폴더를 연결한다. | 작업 지침과 문서의 위치를 정리한다. |
| 업무 목록 | 평소 업무와 목표를 적고 하나를 고른다. | 업무 목록을 저장한다. |
| 직접 수행과 기록 | 업무를 한 번 진행하며 과정·판단을 전달한다. | 시간순 활동 기록과 업무 상태를 남긴다. |
| 워크플로우 | 업무 순서 정리를 요청한다. | 시작부터 완료까지 순서와 역할을 정리한다. |
| 업무 가이드 | 목표·선호·참고 자료를 알려준다. | 각 단계에서 좋은 결과를 만드는 기준을 정리한다. |
| 기록 양식 | 목표에 맞는 양식을 요청한다. | 나중에 사용할 빈 성과 기록 양식을 만든다. |
| 스킬·하네스 | 필요한 판단과 설정을 한다. | 자료를 사용하는 지침과 실제 실행 환경을 갖춘다. |
| 검토 전달 경로 | 검토할 곳과 답변할 곳을 정한다. | 승인 대기함을 연결하고 요청·답변을 기록한다. |
| 자동 시작과 시험 | 일정과 실행 범위를 정한다. | 정기 실행을 설정하고 별도 시험으로 확인한다. |
| 운영과 개선 | 초안을 검토하고 결과를 평가한다. | 승인된 실행, 성과 기록, 개선 기준 반영을 수행한다. |

앞 단계에서 아직 선택하지 않은 업무를 이미 선택한 것으로 취급하거나, 아직 만들지 않은 승인 대기함이 있다고 가정하지 않는다. 단계를 옮기면 제목 번호뿐 아니라 도입 문장·프롬프트·테스트·단계 참조까지 함께 고친다.

당장 하지 않아도 되는 문제와 후속 작업은 맨 뒤 ‘기타’에 별도 문서로 기록하도록 안내한다. 핵심 흐름 중간에 문제 분석·개선 과제를 길게 끼워 넣지 않는다.

## 5. 단계별로 담을 내용

### 5-1. 준비와 작업 연결

필수 계정·앱·작업 공간만 안내한다. 로그인과 작업 폴더 열기처럼 AI가 대신할 수 없는 최소 조작은 쉽게 설명한다. 사용할 환경이 달라질 수 있는 메뉴와 연결 방식은 확인된 환경에 맞춰 적는다.

초보자가 운영체제의 앱 이름을 안다고 가정하지 않는다. 예를 들어 ‘파일 탐색기나 Finder에서 폴더를 만든다’보다 ‘내 컴퓨터 원하는 곳에 폴더를 만든다’라고 쓴다. 특정 앱이나 메뉴 이름이 행동에 꼭 필요할 때만 무엇을 여는 곳인지 함께 설명한다.

한 번호에 여러 화면의 조작을 몰아넣지 않는다. 메뉴 열기, 선택, 다음 버튼 누르기, 이름 입력, 폴더 추가, 생성은 따라가기 쉬운 번호로 나눈다. 번호마다 지금 해야 할 행동이 분명해야 한다. 폴더의 용도처럼 조작 자체가 아닌 설명은 목록 밖에 따로 쓴다.

폴더와 프로젝트 이름은 업무 내용을 짐작할 수 있으면서 짧게 정한다. Threads 계정 운영에는 `ai-system`처럼 범위가 넓은 이름보다 `threads`가 적절하다. 구체적으로 보이게 하려고 목적·도구·작업 범위를 전부 붙여 이름을 길게 만들지 않는다. 이름을 바꾸면 폴더 생성 안내, 프로젝트 이름, 선택할 폴더, 프롬프트의 조건과 경로도 함께 맞춘다. 다른 카드에서는 해당 업무에 맞는 이름을 사용한다.

완성될 전체 폴더 구조와 파일 목록을 앞에 길게 나열하지 않는다. 필요한 문서는 해당 단계에서 AI가 만들도록 한다. 파일 이름이 꼭 필요하다면 역할을 함께 짧게 설명한다.

### 5-2. 업무 목록과 선택

평소 업무를 전부 적고, 중요도 순으로 나열한 뒤 번호를 붙인다. 목록에 목표를 포함해 이후 가이드와 성과 측정의 기준으로 재사용한다.

현재 예시 열 순서는 ‘번호 → 업무 → 목표 → 결과물 → 중요도 → 반복 주기 → 시간 오래 걸리는 부분’이다. 중요도는 1~5점이고 중요한 업무일수록 높은 점수다. 표만 바꾸지 말고 위의 작성 안내도 열 구성과 맞춘다. 표가 넓으면 가로 스크롤을 허용한다.

‘목표’는 이루려는 변화이고 ‘결과물’은 업무로 만들어지는 것이다. 예를 들어 팔로워 증가와 게시글 한 편은 구분한다. 중요도가 높거나 자주 반복하는 업무 중 사람이 직접 선택하고, 선택한 뒤 AI에게 알려준다.

### 5-3. 직접 업무를 하며 기록

업무를 처음부터 끝까지 하면서 그때그때 채팅으로 알려준다. 한꺼번에 회상해 요약하는 방식만 안내하지 않는다. 무엇을 했는지, 왜 그렇게 했는지, 막힌 부분, 해결하려고 한 일, 결과물, 사용한 다른 AI와 도구를 포함한다.

실제 작업 시각과 보고한 시각을 혼동하지 않도록 한다. 게시나 제출 이후 기다리는 기간에는 기록을 멈추고, 결과가 나온 뒤 필요한 정보만 다시 전달하게 한다.

### 5-4. 워크플로우와 업무 가이드

워크플로우는 일의 순서, 가이드는 각 단계에서 판단하고 작성하는 기준이다. 둘을 같은 설명으로 반복하지 않는다. ‘제목 작성 → 본문 작성’이라는 순서와 ‘어떤 제목이 좋은가’라는 기준의 차이를 예시로 보여줄 수 있다.

AI에게 이미 알려준 업무 과정에서 정리할 수 있는 내용은 직접 정리하게 하고, 부족한 기준은 질문하게 한다. 참고 자료를 독자가 미리 파일로 정리할 필요는 없다. AI가 접근할 수 있는 자료는 확인하고, 직접 볼 수 없는 것은 전달 방법을 안내하게 한다.

기존 결과물이 많은 경우에는 성과와 특징을 비교한다. 적거나 없는 경우에는 목표·독자·원하는 방식과 참고 사례로 첫 초안을 만든다. 자료가 없다고 가이드 작성을 중단시키지 않는다. 참고 사례가 없어도 현재 답변으로 초안을 만들고 이후 시험할 수 있다.

### 5-5. 성과 양식

기록할 항목과 뜻, 확인 방법을 목표에 맞게 정하고 빈 양식을 AI가 만들게 한다. 양식 예시는 설명만 하지 말고 박스 안에 실제 모습을 보여준다.

Threads 사례에는 링크·주제·제목과 본문·게시 시각·확인 시각·경과 시간·조회수·좋아요·댓글·공유·확인 가능한 팔로우 수·사용한 가이드·새 시도 등을 넣었다. 다른 업무에는 구매 전환, 제작 시간, 수정 횟수, 사용자 평가 등 실제 확인할 수 있는 항목을 사용한다.

### 5-6. 스킬·하네스·검토 경로

스킬은 업무 방법과 참고 자료를 묶은 지침이다. 기존 워크플로우·가이드를 찾아 사용하도록 만들고, 자료 본문을 여러 파일에 중복 복사하도록 하지 않는다.

하네스는 도구·접근 권한·진행 상황 저장·중단과 재개 방법 등을 갖춘 실행 환경이다. 어떤 도구가 가능한지부터 확인하고, 사람이 해야 할 로그인·권한 설정만 하나씩 안내하게 한다.

승인 대기함은 자동 실행 전에 갖춘다. 현재 사례에서는 스킬·하네스 준비 뒤에 배치했다. 첫 작업부터 복잡한 승인 데이터베이스를 만들게 하지 않는다. 본문의 표·프롬프트·실제 도구 구성이 서로 맞아야 한다.

### 5-7. 자동 시작·시험·실제 운영

사람이 매번 시작을 요청하는 방식과 일정에 맞춰 자동 실행되는 방식을 구분한다. 일정에는 요일·시각·시간대를 넣고, 설명과 복사할 프롬프트를 일치시킨다. 예시는 독자가 바꿀 수 있게 안내한다.

실행 시 필요한 주제·자료를 미리 확보하는 방법도 정한다. 사람의 실시간 답변이 없어도 진행할 범위와 멈출 조건을 정한다. 로컬 파일·앱·계정이 예약 실행 환경에서 실제로 사용 가능한지 확인하게 한다.

정기 일정과 별도로 가까운 시간에 1회 시험을 요청한다. 시험에서는 실제 게시 등 외부 실행을 하지 않고 결과가 지정된 곳에 도착하는지 확인한다. 실패하면 원인을 확인하고 해결한 뒤 다시 시험하며, 정상 정기 일정은 유지한다.

최종 승인 뒤의 실행, 실행 결과 기록, 성과 측정, 가이드 개선까지 연결한다. 같은 시점의 수치끼리 비교하고, 자료가 부족하면 판단을 유보한다. 다음에 바꿔볼 것을 하나 제안하고 사람의 선택을 받아 반영하도록 한다.

<a id="section-6"></a>

## 6. 프롬프트 작성 기준

프롬프트는 독자가 복사해 사용할 수 있는 요청문이다. 본문과 같은 일을 요청해야 하며, 읽지 않은 표나 전달하지 않은 자료를 AI가 이미 알고 있다고 가정하지 않는다. ‘위 표를 사용해줘’라고 쓴다면 표도 함께 전달하는 방법을 안내하거나 필요한 열을 프롬프트 안에 포함한다.

| 포함할 요소 | 작성 방법 |
| --- | --- |
| 목표·할 일 | 지금 단계에서 무엇을 만들거나 실행할지 직접 적는다. |
| 기존 맥락 | 앞 단계의 목표·워크플로우·가이드·기록을 참고하게 한다. |
| 부족한 정보 | 기존 내용은 요약하고, 추가로 필요한 것은 질문하게 한다. |
| AI가 할 일 | 만들기·정리·저장·접근 가능 자료 확인은 직접 수행하게 한다. |
| 사람이 할 일 | 직접 해야 하는 조작만 위치와 행동을 하나씩 알려주게 한다. |
| 결과물 | 문서·양식·초안·승인 항목 등 무엇이 나와야 하는지 적는다. |
| 실행 경계 | 초안만 작성, 승인 후 게시, 시험 중 게시 금지 등 해당 단계의 범위를 적는다. |
| 대안 | 자료 접근이나 도구 연결이 안 될 때 사람이 전달하는 방식 등을 안내하게 한다. |

기본 표현 예시는 다음과 같다. 모든 프롬프트에 전부 붙이지 말고 필요한 부분만 사용한다.

```text
앞서 정한 목표와 지금까지의 기록을 참고해줘.
이미 파악한 내용은 짧게 요약하고 추가로 필요한 것은 나에게 물어봐.
네가 만들거나 정리할 수 있는 것은 직접 해줘.
내가 해야 할 일은 어디에서 무엇을 해야 하는지 하나씩 쉽게 알려줘.
기존 자료가 있다면 새로 중복 생성하지 말고 사용해줘.
```

프롬프트는 본인 상황에 맞게 바꿔 사용하도록 안내한다. 변경할 내용은 `[현재 개수]`, `[게시글 링크]`처럼 분명한 빈칸으로 표시한다. 초보자가 채울 수 없는 경로·ID를 미리 요구하지 않는다.

<a id="section-7"></a>

## 7. 설명·대화 예시·표·양식 작성법

### 설명과 예시의 역할

설명은 다음 행동을 안내한다. 대화 예시는 실제 채팅창에 어떻게 쓰는지 보여준다. 표는 비교나 기록 구조를 보여준다. 양식 박스는 실제 결과물이 어떤 모습인지 보여준다. 같은 설명을 이 네 곳에서 반복하지 않는다.

대화 예시는 실제 말투로 구체적인 행동·판단을 보여준다. ‘검색어를 바꿨다’보다 ‘요금 폭탄으로 검색했는데 적당한 사례가 없어서 AI 구독료로 다시 검색했어’처럼 쓴다. 다른 AI의 답을 참고했다면 무엇을 요청했고 무엇을 선택했는지 포함한다.

상세 페이지의 설명은 친근하고 일관된 ‘해요’체로 쓴다. 설명은 ‘AI여야 해요’처럼, 행동 안내는 ‘아래 요청문을 붙여넣어주세요’처럼 쓴다. 딱딱한 말투가 주는 심리적 부담을 줄이되 과도한 감탄이나 장식으로 분량을 늘리지 않는다. ‘나.’의 대화 예시와 복사할 프롬프트는 자연스러운 채팅 말투를 유지한다. 이는 기존 서술체 기준을 바꾸는 2026-11-24 사용자 피드백이다.

‘작업할 폴더를 선택하는 곳’처럼 위치를 다시 추측해야 하는 표현도 피한다. 초보자가 조작할 화면을 찾을 수 있도록 확인된 메뉴 이름과 누르는 순서를 안내한다. 공식 안내를 확인했더라도 독자 앱의 버전·언어에 따라 표기가 달라질 수 있음을 고려한다. 확인한 안내는 [Codex 프로젝트 열기](https://learn.chatgpt.com/training/codex-lab/index.html?step=project)처럼 출처를 남긴다.

### 양식·프롬프트 박스

복사해서 입력할 요청문과 AI가 만들어주는 결과물 샘플을 구분해 이름을 붙인다. 둘 다 박스여도 역할이 다르다. 텍스트 요청문은 `text` 코드 블록을 사용한다. 사용자가 메시지에 붙인 `rust` 같은 표시는 실제 프로그래밍 언어가 필요한 내용인지 확인한다.

성과가 없는 예시에는 수치를 지어 넣지 않는다. 빈 양식을 보여준다. 가상 수치를 이용한 별도 연습·계산은 핵심 흐름에 필요하지 않으면 넣지 않는다.

### 표

표에 열을 추가하면 헤더·구분선·모든 행의 열 개수와 위아래 설명을 함께 수정한다. 번호는 업무를 가리킬 때 실제 번호와 맞춘다. 중요도 척도, 입력값, 열의 의미를 필요한 만큼 설명한다.

외부 서비스의 표 구성을 소개한다면 실제 이름·유형·선택지를 조회해서 맞춘다. 문서에 적힌 표와 실제 계정이 같다고 추측하지 않는다. 실제 계정에서 확인한 내용은 확인 시점의 사례이며 모든 독자의 기본 구성은 아니다.

<a id="section-8"></a>

## 8. 사람의 판단과 AI 실행·승인 연결

현재 Threads 사례에서 사용자가 정한 방식은 **Notion에서 검토 → Codex 채팅에서 수정 요청 또는 승인 → Codex가 Notion에 답변과 상태 기록 → 승인된 다음 절차 실행**이다. 같은 글 안에서 ‘Notion 상태를 사람이 바꿔 승인’하는 방식을 섞지 않는다.

최종 초안을 승인하면 추가 게시 요청을 기다리지 않고 게시하도록 설정했다면, 그 규칙을 실제 프롬프트에도 넣는다. 설명만 ‘자동 게시된다’고 쓰면 안 된다. 초안 검토와 게시 권한 확보가 필요하며, 시험 실행에서는 게시하지 않는다는 범위도 일치시킨다.

승인 요청에는 검토 내용, 고유한 요청 ID, 확인자, 상태를 남긴다. 같은 요청을 중복 생성하지 않고, 승인 내용과 처리 결과를 기록한 뒤 완료 처리한다. 어떤 초안에 대한 답변인지 모호하면 AI가 물어보도록 한다.

다른 업무에서는 게시 대신 발송·공유·납품·배포 등 실제 외부 실행에 맞게 바꾼다. 모든 업무에 동일한 승인 단계 수나 도구를 강요하지 않는다.

Notion의 사용자 알림과 Codex의 승인 감지는 다른 문제다. ‘확인자’ 지정, 알림 설정, 앱·메일 수신 여부를 확인하지 않고 알림이 전혀 없다고 단정하지 않는다. 사람이 Notion 상태를 바꿨다고 Codex 실행이 자동 재개된다고도 단정하지 않는다. 웹훅·연결 도구·폴링 등 추가 연결이 필요한지는 실제 구성으로 판단한다.

## 9. 정확성과 독자별 상황 차이

- 기존 작업물이 없는 경우에도 진행할 수 있는 첫 가이드를 제시한다. 경험자 경로만 쓰지 않는다.
- ‘10개 이상 / 0~9개’처럼 상황을 나누면 경계에서 빠지는 독자가 없도록 제목·본문·프롬프트를 모두 맞춘다. 10개는 현재 사례의 안내 기준이며 보편적인 성과 분석 기준이 아니다.
- 앞 단계의 실습으로 작업물이 하나 생겼더라도 독자가 무슨 기준으로 경로를 선택할지 알 수 있게 설명한다.
- AI가 웹페이지·계정 지표·로컬 파일에 접근할 수 있다고 가정하지 않는다. 현재 도구·권한부터 확인하고 대체 전달 방법을 제시한다.
- 예약 실행 등록과 실행 성공을 구분한다. 컴퓨터·앱이 켜져 있어야 하는지, 예약 환경에서 스킬과 자료를 읽을 수 있는지 확인하게 한다.
- 실제 작업 시각·게시 시각·보고 시각·측정 시각을 구분한다. 알려주지 않은 시각을 AI가 알고 있는 예시를 만들지 않는다.
- 확인할 수 없는 수치는 ‘미확인’으로 남긴다. 수치 0과 미확인을 혼동하지 않는다. 계정 전체 증가와 특정 게시물에 귀속된 증가도 구분한다.
- 확인한 몇 개의 특징을 성공 법칙으로 단정하지 않는다. 처음 만든 가이드는 시험할 초안이고, 운영 결과로 개선한다.
- 도구 메뉴·기능·유료 여부는 작성 시 공식 안내나 실제 연결 상태로 확인한다. 확인하지 못한 내용은 확정된 사실로 쓰지 않는다.
- 다른 AI를 사용하는 단계는 실제 업무에 필요할 때 넣는다. 특정 제품을 모든 독자의 필수 준비물로 만들지 않는다.

## 10. 문체·용어·제목·읽기 편한 구성

### 한 화면의 정보량과 심리적 부담 줄이기

넓은 여백은 Step과 다음 Step 사이를 구분할 때 사용한다. 페이지 제목과 첫 Step 제목 사이에는 같은 크기의 여백을 적용하지 않는다. 첫 Step 앞의 큰 상단 마진·패딩과 구분선은 제거하고, 페이지 제목의 기본 아래 여백만 유지해 첫 내용을 바로 읽을 수 있게 한다.

상세 페이지의 본문에서는 `Step` 제목 앞에만 `📌`을 붙인다. 페이지 제목, Step 안의 소제목, ‘기타’ 등에는 붙이지 않는다. 왼쪽 ‘이 글의 순서’ 목차에도 이모지를 붙이지 않는다. 목차는 폭이 좁고 항목이 길어지기 쉬우므로, 본문과의 장식적 일관성보다 짧고 쉽게 훑어볼 수 있는 구성을 우선하는 사용자 승인 예외다. 주요 단계의 경계를 친근하게 알아볼 수 있도록 하려는 사용자의 편집 방향이다. 제목마다 서로 다른 이모지를 늘리거나 본문 문장마다 장식하지 않는다. 아이콘은 제목 문구를 대체하지 않으며, 인지부하 감소가 검증된 효과라고 단정하지 않는다. 현재 페이지는 생성 과정에서 아이콘을 붙이므로 원문 제목에 중복으로 추가하지 않는다.

Step 사이 구분선의 위아래 여백은 동일하게 맞춘다. 단순히 margin과 padding을 따로 늘리지 말고, 앞 내용의 아래 여백과 다음 제목의 위 여백까지 고려해 실제 간격이 균형을 이루게 한다. 현재 상세 페이지는 넓힌 전체 간격을 유지하면서 구분선 양쪽에 같은 여백 값을 사용한다.

초보자가 한 화면에서 너무 많은 내용을 한꺼번에 읽고 판단하지 않도록 구성한다. 내용을 쉽게 풀어 쓰는 것만으로 충분하다고 생각하지 않는다. 지금 해야 할 행동과 핵심 내용을 먼저 보여주고, 세부 설명은 관련 소제목에서 나눠 보여준다. 글이 빽빽해 보여 시작하기 어렵게 느껴지지 않도록 정보의 양과 여백을 함께 살핀다.

내용의 관계에 맞춰 다음 표현을 우선 검토한다. 긴 문단을 그대로 표의 한 셀에 옮겨 넣는 것은 정보량을 줄이는 방법이 아니다.

| 내용 | 권장 표현 |
| --- | --- |
| 여러 조건·방법의 비교 | 같은 기준으로 비교하는 간결한 표 |
| 병렬인 준비물·확인 사항 | 짧은 불릿 목록 |
| 실제로 따라 할 조작 | 행동 하나씩 나눈 번호 목록 |
| 단계의 연결·분기·반복 | 간단한 흐름도나 다이어그램 |
| 복사할 요청문·결과 양식 | 역할이 표시된 별도 박스 |
| 이유·맥락 설명 | 핵심만 담은 짧은 문단 |

모든 문장을 억지로 시각화하지 않는다. 독자가 핵심과 관계를 더 빨리 파악할 수 있는 표현을 선택하고, 한 표·한 다이어그램에도 너무 많은 내용을 담지 않는다. 정보량이 많으면 목적별로 나눈다. 원문에 필요한 조건이나 내용을 임의로 삭제하지 않는다.

Step 사이에는 충분한 여백을 두어 앞 단계가 끝나고 다음 단계가 시작된다는 것을 느낄 수 있게 한다. 2026-11-24 사용자 요청으로 현재 상세 페이지의 장 제목 앞 여백과 구분선 아래 패딩을 기존의 3배로 넓혔다. 구체적인 수치는 `src/article.css`를 기준으로 관리한다. 다른 카드도 같은 상세 페이지 스타일을 재사용하고, 모바일에서도 간격을 유지한다. 모든 내부 문단과 표의 패딩까지 일괄 3배로 늘리라는 뜻은 아니다.

제목은 독자가 할 일을 짧고 구체적으로 나타낸다. 현재 수정에서는 ‘목표와 완료 조건 정하기’를 ‘목표와 완료 조건 알려주기’로, ‘성과를 전달하기’를 ‘성과 알려주기’로 바꿨다. 같은 행동에는 같은 말을 사용한다.

‘스킬 만들기’, ‘업무 가이드 만들기’, ‘성과를 기록할 양식 만들기’처럼 산출물과 행동이 보이게 쓴다. 제목에 작업 내용을 전부 늘어놓지 않는다. 실제 내용이 제목의 범위와 맞는지도 확인한다.

새 용어는 필요할 때 짧게 정의한다. 내부 문서 이름·상태값·ID를 먼저 나열하고 뒤에서 설명하는 방식을 피한다. ‘초안’, ‘확인자로 지정’처럼 쉬운 우리말을 우선한다. 실제 서비스의 ‘확인자’, ‘승인됨’ 같은 필드·상태 이름은 정확하게 유지한다.

같은 의미의 이어지는 설명은 한 문단으로 묶는다. 문장마다 줄을 바꾸지 않는다. 행동 전환, 프롬프트, 상황별 경로가 바뀔 때 문단을 나눈다.

정확한 사용자 문구를 반영하는 수정에서는 임의로 다른 표현을 덧붙이거나 문단을 재작성하지 않는다. 전체 문체를 다듬는 작업이라면 띄어쓰기·인용부호·표기부터 일관되게 정리한다.

단계 목차와 본문 제목을 일치시킨다. 현재 상세 페이지는 스크롤 위치에 따라 목차에서 읽는 항목을 굵게 표시한다. 다른 상세 페이지도 공통 레이아웃과 복사 박스 기능을 재사용하고, 문구 변경만으로 별도 UI를 만들지 않는다. 화면 정책의 기준은 PRD다.

## 12. 다른 카드의 상세 페이지를 만드는 순서

1. 카드의 업무와 최종 결과물을 정한다. Threads 예시의 이름만 바꾸지 말고 실제 작업 순서를 확인한다.
2. 아무것도 준비하지 않은 독자를 기준으로 필요한 계정·도구·자료와 사람이 해야 하는 최소 조작을 정리한다.
3. 이 문서의 전체 흐름을 참고해 단계 목차를 만든다. 앞 단계에서 얻은 정보가 뒤 단계의 입력으로 이어지는지 확인한다.
4. 기존 작업물·성과 자료·접근 도구가 없는 경우의 경로를 정한다. 글 전체를 중복하지 말고 필요한 단계에서 나눈다.
5. 각 단계에 짧은 설명, 복사할 프롬프트, 필요한 대화나 결과물 예시를 넣는다. 예시가 필요 없는 단계에 억지로 넣지 않는다.
6. 주체·시점·승인·자동 실행·기록의 연결을 검수한다. 실제 도구 구성과 기능은 확인한다.
7. 수정안을 요청받았다면 요청된 단계만 제안하고 파일에 먼저 적용하지 않는다. 승인받은 문구와 삭제 범위를 정확히 적용한다.
8. 원문 반영 후 관련 제목·목차·참조·요청문을 함께 확인한다. 한 부분을 삭제하면 같은 역할의 박스와 뒤따르는 설명도 살펴본다.
9. 사용자가 요청한 시점에 빌드하고 확인 범위를 보고한다. ‘빌드하지 마’라는 요청을 지킨다. 빌드는 운영 배포와 다르다.

현재 Thread 상세 페이지는 [원문](../AI_native_system_구축하기_실제사례_보완본%20%281%29.md)과 [변환 스크립트](../scripts/thread-article.mjs)로 생성된다. 준비사항 일부는 변환 스크립트가 추가하고, 원문 서두 일부는 화면에서 제외한다. 검토할 때 원문만 보지 말고 실제 생성되는 글도 확인한다.

현재 로컬 서버는 `dist`를 제공하며 시작할 때 빌드한다. 실행 중 원문만 수정하면 브라우저에는 바로 나타나지 않는다. `npm run build` 후 새로고침해야 한다. 향후 구현이 바뀌면 실제 서버와 빌드 코드를 기준으로 판단한다. 문서만 작성하는 이번 작업에는 사이트 빌드가 필요하지 않다.
