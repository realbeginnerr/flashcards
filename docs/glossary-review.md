## 1. 결과와 검토 방법

- 원본: `0 glossary 단어장 (공통).csv`. 원본 CSV는 변경하지 않았다.
- 원본 용어 238개 → 현재 카드 239개. 승인된 병합 -5개, 기존 11행 분리 +1개, IA 검증기 삭제 -1개, 이번 개념 분리 +6개. 이전 승인 사항을 유지한다.
- 뜻 누락 4개 모두 설명·예시 초안 작성. 코멘트는 이번 첨부에 따라 협업 피드백·코드 주석을 함께 설명했다. 전체 카드에 하나 이상의 분야 제안.
- 분류는 용어와 원문 설명에 근거한 편집 판단이다. 원래 분야 O 표시는 덮어쓰지 않고 JSON에 보존했다.
- 아래 원본 행은 CSV의 논리 레코드 번호이며 2개 헤더 행을 포함한다. 셀 내부 줄바꿈이 있어 텍스트 편집기의 물리적 줄 번호와 다를 수 있다.
- 3장의 병합·맥락 구분안은 사용자 승인 완료. 11행은 사용자 제공 문구로 두 카드 분리, 151행 IA 검증기는 삭제 완료. 154행 스킬은 AI 작업 지침 의미의 정의·예시와 AI 툴 분류가 승인되었다. 이번 첨부의 반영·조정 내역은 7장, 새 정의 9개는 8장에 기록했다. 7·8장의 정의·예시·표기·개념 분리는 사용자 승인 완료다. 5장의 전체 239개 카드 분야 분류도 사용자 승인 완료다. 그 외 내용은 기존 검토 상태를 유지한다. 서비스 공개·운영 데이터 등록은 수행하지 않았다.
- 정리 데이터: [glossary-draft.json](../data/glossary-draft.json). 원본 행·정의·영문 설명·시험일·중요도·비고를 sourceRecords에 보존했다. 삭제된 151행의 원문은 excludedSourceRecords에만 보존하며 카드 목록에서 제외했다.
- 영문 정의는 원문 자료로 보존하고 MVP 카드 표시 필드로 추가하지 않았다. 영문 암기 서비스로 범위를 확장하지 않는다.

## 2. 뜻 누락 4개 보완안

### 코멘트 — 원본 88행

**정의:** 작업물에 설명·의견·피드백 등을 기록한 내용이다. 디자인 협업 도구의 코멘트는 작업물에 의견을 남기는 기능이고, 코드 코멘트인 주석은 코드의 동작이나 의도를 설명하는 글이다. 코드 주석은 일반적으로 실행할 명령으로 처리되지 않는다.

**예시:** Figma: “이 버튼을 조금 크게 만들어 주세요.”
JavaScript 코드 주석: // 로그인 버튼 클릭 시 실행
Figma 코멘트는 주로 협업·피드백에, 코드 주석은 코드 설명에 사용한다. 주석 문법은 프로그래밍 언어에 따라 다르다.

근거: [Figma: Guide to comments](https://help.figma.com/hc/en-us/articles/360039825314-Guide-to-comments-in-Figma), [MDN: JavaScript grammar and types](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Grammar_and_types)

### Git — 원본 186행

파일의 변경 이력을 기록하고 관리하는 분산 버전 관리 시스템이다. 이전 변경을 확인하거나 여러 사람이 작업한 내용을 합치는 데 사용한다. GitHub는 Git 저장소를 온라인에서 관리하고 협업하도록 돕는 별도 서비스다.

예시: 화면 코드를 수정한 이력을 남겨두고, 문제가 생기면 이전 변경과 비교한다.

근거: [Git 공식 사이트](https://git-scm.com/), [GitHub Docs: What is GitHub?](https://docs.github.com/en/get-started/start-your-journey/what-is-github)

### 로컬 — 원본 218행

작업 중인 자신의 컴퓨터나 그 안의 개발 환경을 가리키는 말이다. 로컬에서 실행한다는 것은 외부에 배포하기 전에 자신의 컴퓨터에서 프로그램을 실행해 확인한다는 뜻이다.

예시: 내 컴퓨터에서 개발 서버를 실행하고 localhost 주소로 웹사이트를 확인한다.

근거: [MDN: Local testing server](https://developer.mozilla.org/en-US/docs/Learn_web_development/Howto/Tools_and_setup/set_up_a_local_testing_server)

### 개발 — 원본 219행

사용자의 요구를 실제로 동작하는 웹사이트·앱·프로그램으로 구현하고, 테스트·배포·유지보수하는 활동이다. 코드를 작성하는 일뿐 아니라 작동을 확인하고 개선하는 과정도 포함한다.

예시: 플래시카드의 뒤집기 동작을 구현하고, 학습 기록 저장이 제대로 되는지 확인한다.

근거: [IBM: What is software development?](https://www.ibm.com/think/topics/software-development)

### 154행 — 스킬 승인·반영 완료

#### 뜻

AI에게 특정 작업을 어떤 순서와 기준으로 수행해야 하는지 알려주는 작업 지침 묶음이다. 필요에 따라 참고 문서, 보조 프로그램, 이미지 같은 자료를 함께 담을 수 있다. 예를 들어 디자인 스킬에 색상·글꼴 기준과 화면을 검토하는 순서를 적어두면, AI가 그 지침을 참고해 작업하도록 도울 수 있다. 모든 AI 도구가 스킬을 같은 방식으로 지원하거나 구성하는 것은 아니다.

#### 예시: 웹사이트 디자인 스킬

- 작업 지침: 사용할 색상·글꼴과 디자인 검토 순서를 적는다.
- 참고 자료: 디자인 시스템과 컴포넌트 사용 기준을 넣는다.
- 보조 도구: 결과를 확인하는 검사 프로그램을 함께 둘 수 있다.

폴더 구조는 다음과 같이 구성할 수 있다. 원본 비고의 예시를 보존했다.

```text
design-skill/
│
├── SKILL.md
│
├── references/
│   ├── design-system.md
│   ├── typography.md
│   ├── color-palette.md
│   ├── layout-spacing.md
│   └── components.md
│
├── scripts/
│   ├── validate-design.py
│   └── generate-assets.py
│
├── assets/
│   ├── logo.svg
│   ├── icons/
│   └── templates/
│
└── examples/
    ├── good-example.png
    └── bad-example.png
```

`SKILL.md`는 작업 지침, `references`는 참고 문서, `scripts`는 보조 프로그램, `assets`는 이미지 등의 자료, `examples`는 결과 예시를 담는 구성의 한 예다.

**모든 폴더를 반드시 만들어야 하는 것은 아니며, 모든 AI 도구가 이 구조를 똑같이 사용하는 것은 아니다.**

AI 툴 분야로 분류하며, 이 항목의 정의·예시·분류는 승인 완료다.

**예시:** 질문에 답하거나 글을 작성하는 서비스, 이미지를 생성하는 서비스 등이 있다. 모델이 자동차 엔진이라면 제품은 엔진과 조작 장치 등을 갖춘 자동차에 비유할 수 있다.

### AI 모델 — 원본 51행

**정의:** 데이터에서 학습한 패턴을 이용해 입력에 대한 예측·분류·생성 등의 결과를 만드는 인공지능의 핵심 구성 요소다. 모든 AI 모델이 글이나 이미지를 생성하는 것은 아니다.

**예시:** 문장을 생성하는 언어 모델, 이미지 속 대상을 분류하는 모델 등이 있다. 제품은 사용자가 이용하는 서비스이고, 모델은 그 안에서 정보를 처리하는 기술이다.

근거: [IBM: AI inference](https://www.ibm.com/think/topics/ai-inference)

### 라이브러리 (디자인) — 원본 74행

**정의:** 자주 사용하는 디자인 요소·스타일·변수 등을 모아 필요할 때 재사용할 수 있도록 관리하는 모음이다. 개발 라이브러리와 재사용이라는 공통점이 있지만 담는 대상과 사용하는 방식이 다르다.

**예시:** Figma에서 버튼·입력창 등의 컴포넌트를 라이브러리로 공유해 여러 디자인 파일에서 사용한다.

### 탭 (터치 동작) — 원본 86행

**정의:** 스마트폰이나 태블릿 등의 화면을 손가락으로 가볍게 한 번 터치하는 동작이다.

**예시:** 스마트폰의 로그인 버튼을 손가락으로 한 번 누른다.

### 탭 (UI 요소) — 원본 86행

**정의:** 같은 화면 영역에 있는 여러 콘텐츠 묶음 중 하나를 선택해 보여주도록 하는 UI 요소다.

**예시:** 상품 상세 화면의 상세정보 / 리뷰 / 문의 중 리뷰 탭을 선택하면 그 영역에 리뷰가 표시된다. Tap은 동작이고 Tab은 구성 요소이므로 Tab을 Tap할 수 있다.

근거: [W3C: Tabs Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)

### 코멘트 — 원본 88행

**정의:** 작업물에 설명·의견·피드백 등을 기록한 내용이다. 디자인 협업 도구의 코멘트는 작업물에 의견을 남기는 기능이고, 코드 코멘트인 주석은 코드의 동작이나 의도를 설명하는 글이다. 코드 주석은 일반적으로 실행할 명령으로 처리되지 않는다.

**예시:** Figma: “이 버튼을 조금 크게 만들어 주세요.”
JavaScript 코드 주석: // 로그인 버튼 클릭 시 실행
Figma 코멘트는 주로 협업·피드백에, 코드 주석은 코드 설명에 사용한다. 주석 문법은 프로그래밍 언어에 따라 다르다.

근거: [Figma: Guide to comments](https://help.figma.com/hc/en-us/articles/360039825314-Guide-to-comments-in-Figma), [MDN: JavaScript grammar and types](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Grammar_and_types)

### 변수 — 원본 115행

**정의:** 값에 이름을 붙여 저장하고 재사용하는 수단이다. 프로그래밍에서는 데이터를 계산이나 동작에 사용하고, Figma에서는 색상·숫자·문자열·불리언 등의 값을 관리해 디자인 속성에 적용한다. 역할과 지원 방식은 사용하는 언어·도구에 따라 다르다.

**예시:** primaryColor라는 이름으로 파란색 값을 관리하고 여러 버튼에서 재사용한다. Figma에서는 모드별 값을 설정해 밝은 테마와 어두운 테마에 적용할 수 있다. Figma 변수로 디자인 토큰을 구현할 수도 있지만 변수와 디자인 토큰은 동일한 개념은 아니다.

근거: [Figma: Variables, collections, and modes](https://help.figma.com/hc/en-us/articles/14506821864087-Overview-of-variables-collections-and-modes), [MDN: JavaScript grammar and types](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Grammar_and_types), [Design Tokens Community Group: Glossary](https://www.designtokens.org/glossary/)

### 상수 — 원본 115행

**정의:** 프로그램에서 한 번 정한 값을 다른 값으로 다시 할당할 수 없도록 다루는 이름 또는 값이다. JavaScript의 const는 선언한 이름에 다른 값을 재할당하지 못하게 한다. 단, 객체·배열 내부까지 자동으로 변경 불가능하게 만드는 것은 아니다.

**예시:** const MAX_ITEMS = 10; 이후 MAX_ITEMS = 20으로 다시 할당할 수 없다. const settings = { dark: false }에서는 settings에 다른 객체를 재할당할 수 없지만 settings.dark 값은 변경할 수 있다.

근거: [MDN: const](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/const)

### 디자인 토큰 — 원본 128행

**정의:** 디자인 시스템에서 색상·글자 크기·간격 등의 디자인 결정을 이름과 값으로 표현하고 일관되게 관리·공유하는 단위다.

**예시:** color-primary = #0050FF로 브랜드 색상에 이름을 붙여 여러 화면에서 재사용한다. Figma 변수는 이러한 디자인 값을 적용하는 구현 수단이 될 수 있다.

근거: [Design Tokens Community Group: Glossary](https://www.designtokens.org/glossary/), [Figma: Variables, collections, and modes](https://help.figma.com/hc/en-us/articles/14506821864087-Overview-of-variables-collections-and-modes)

### AI 토큰 — 원본 128행

**정의:** AI 모델이 입력과 출력을 처리할 때 사용하는 단위다. 텍스트에서는 단어 전체, 단어 일부, 글자나 문장부호 등이 토큰이 될 수 있다. 토큰 수는 모델과 처리 방식에 따라 달라지며, 일부 서비스의 입력 한도·사용량·비용 산정에도 사용된다.

**예시:** 긴 문서는 여러 토큰으로 나뉘어 처리된다. 한 단어가 항상 한 토큰인 것은 아니다. 여기서는 텍스트 중심으로 설명하며, 일부 모델은 이미지 등 다른 입력도 토큰 단위로 다룬다.

근거: [Google: Understand and count tokens](https://ai.google.dev/gemini-api/docs/tokens)

### 접근 토큰 — 원본 128행

**정의:** 프로그램이 허용된 범위의 데이터나 기능에 접근할 때 제시하는 디지털 자격 정보다. API 요청 등에서 접근 권한을 확인하는 데 사용된다. 디자인 토큰·AI 토큰과는 다른 개념이다.

**예시:** SNS 서비스가 발급한 접근 토큰을 프로그램이 API 요청에 함께 보내, 허용된 범위의 데이터를 가져온다. 실제 토큰 값은 외부에 공개하지 않는다.

근거: [IETF: OAuth bearer token usage](https://www.rfc-editor.org/rfc/rfc6750)

### 행동 맵핑 — 원본 144행

**정의:** 사람들이 특정 공간에서 언제, 어디서, 어떤 행동을 하는지 관찰하고 지도·도면 등 공간 표현에 기록해 패턴을 파악하는 조사 방법이다. 평행좌표 그래프와는 다른 개념이다.

**예시:** 매장에서 고객이 오래 머무는 진열대와 이동 경로를 매장 도면 위에 표시한다. 디지털 화면의 클릭·시선 기록은 목적에 따라 클릭맵·히트맵 등의 용어로 구분해 설명할 수 있다.

근거: [연구: Behavioral observation and spatial mapping](https://pmc.ncbi.nlm.nih.gov/articles/PMC10350905/)

### 평행좌표 그래프 — 원본 144행

**정의:** 여러 변수에 각각 나란한 축을 두고, 하나의 데이터 항목이 각 축에서 갖는 값을 선으로 연결해 비교하는 시각화 기법이다. 여러 항목의 패턴과 차이를 살펴볼 때 사용한다.

**예시:** 고객별 나이·구매 금액·방문 횟수·만족도를 각각 축으로 놓고 고객 한 명당 선 하나로 연결한다. 행동의 위치를 기록하는 행동 맵핑과는 다르다.

근거: [IBM: Parallel coordinates](https://www.ibm.com/docs/en/spss-statistics/30.0.0?topic=types-parallel-coordinate-type-gpl)

### 머메이드 — 원본 152행

**정의:** 텍스트로 작성한 문법을 플로차트·시퀀스 다이어그램 등의 도식으로 표현하는 도구이자 문법이다. AI 기술 자체는 아니지만, AI가 다이어그램용 코드를 작성할 때 활용할 수 있다.

**예시:**

```text
flowchart TD
  A[로그인 화면] --> B[정보 입력]
  B --> C{정보 일치?}
  C -->|예| D[로그인 성공]
  C -->|아니요| E[오류 메시지]
```

Mermaid를 지원하는 도구에서 이 코드를 도식으로 표시할 수 있다.

근거: [Mermaid: Introduction](https://mermaid.js.org/intro/), [Mermaid: Flowchart syntax](https://mermaid.js.org/syntax/flowchart.html)

### 라이브러리 (개발) — 원본 165행

**정의:** 자주 사용하는 코드와 기능을 모아 프로그램에서 재사용할 수 있게 만든 모음이다. 디자인 라이브러리와 재사용이라는 공통점이 있지만, 개발에서는 실제 동작을 구현하는 코드를 사용한다.

**예시:** 그래프를 처음부터 모두 구현하는 대신 Chart.js 같은 차트 라이브러리를 사용한다.

## 8. 어셈블리어부터 샌드박스까지 정의 제안

**상태: 사용자 승인 완료.** 요청 범위는 4장 후반 검토 목록의 다음 9개 용어로 해석했다. 원본 193~238행 사이의 모든 용어를 일괄 수정한 것은 아니다. 정의·예시 초안은 정리 JSON에도 반영했고 원문은 보존했다.

PaaS·IaaS 표기는 첨부 지적과 공식 용어에 맞췄다. 기존 PASS·IASS는 sourceRecords에 남아 있다. PR은 마케팅의 홍보와 혼동하지 않도록 개발 맥락을 이름에 표시했다. 9개 정의·예시·표기는 사용자 승인 완료로 기록했다. 서비스 공개·운영 데이터 반영은 수행하지 않았다.

### 어셈블리어 — 원본 193행

**정의:** 컴퓨터의 기계어 명령에 가까운 작업을 사람이 읽을 수 있는 짧은 명령어로 표현하는 저수준 프로그래밍 언어다. 일반적으로 어셈블러를 통해 기계어로 변환하며, 명령과 문법은 CPU 구조와 도구에 따라 달라진다.

**예시:** ADD 같은 명령으로 값을 더하는 작업을 표현한다. 입문 단계에서는 하드웨어에 가까운 언어라는 개념을 이해하는 정도로 학습할 수 있다.

근거: [Arm: Hello world in assembly](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/hello-world-in-assembly)

### PaaS — 원본 212행

**정의:** 앱을 개발·배포·실행하는 데 필요한 플랫폼을 클라우드 서비스로 제공하는 방식이다. 제공자가 기반 인프라와 실행 환경의 일부를 관리하고, 사용자는 주로 앱 코드와 데이터를 관리한다.

**예시:** 관리형 앱 실행 플랫폼에 코드를 배포하면 직접 서버 하드웨어와 운영체제를 설치·관리하는 부담을 줄일 수 있다. 관리 범위는 서비스에 따라 다르다.

근거: [IBM: IaaS, PaaS, SaaS](https://www.ibm.com/think/topics/iaas-paas-saas)

### IaaS — 원본 213행

**정의:** 서버의 컴퓨팅 자원, 저장 공간, 네트워크 같은 IT 인프라를 클라우드에서 필요한 만큼 이용하는 방식이다. 물리 장비는 제공자가 관리하고, 사용자는 일반적으로 운영체제와 앱 등을 관리한다.

**예시:** 가상 서버를 빌려 운영체제와 웹서버를 설치한다. 서버만을 뜻하는 것이 아니라 저장소·네트워크 등의 자원도 포함한다.

근거: [IBM: IaaS, PaaS, SaaS](https://www.ibm.com/think/topics/iaas-paas-saas)

### PR (개발) — 원본 226행

**정의:** 작성한 코드 변경 사항을 다른 브랜치에 합치기 전에 검토하고 논의할 수 있도록 제안하는 요청이다. 개발자가 컴퓨터에 내리는 일반 명령을 뜻하는 것은 아니다.

**예시:** 버튼 오류를 수정한 브랜치로 PR을 열면 동료가 변경 내용을 검토한다. 자동 테스트나 자동 병합은 설정에 따라 사용할 수 있으며 필수 조건은 아니다. 마케팅의 PR(Public Relations, 홍보)과는 다른 뜻이다.

근거: [GitHub: About pull requests](https://docs.github.com/en/pull-requests/get-started/about-pull-requests)

### n8n — 원본 227행

**정의:** 여러 앱·서비스·API를 연결해 반복 업무를 자동으로 처리하는 워크플로를 만드는 도구다. AI 기능을 연결할 수도 있지만 모든 자동화에 AI가 필요한 것은 아니다.

**예시:** 문의가 접수되면 AI로 내용을 분류한 뒤 담당자에게 전달하는 흐름을 구성한다. 단순히 접수 내용을 표에 저장하는 흐름은 AI 없이도 만들 수 있다.

근거: [n8n Docs](https://docs.n8n.io/)

### 메이크 — 원본 228행

**정의:** 앱과 서비스를 시각적으로 연결해 데이터 전달·변환·알림 등의 작업을 자동화하는 도구다. 자동화 흐름을 시나리오라고 부르며, 필요하면 AI 기능도 연결할 수 있다.

**예시:** 폼 응답이 들어오면 스프레드시트에 저장하고 팀에 알림을 보낸다. 여기에 AI 요약 단계를 추가할 수도 있다. 모든 시나리오가 AI를 사용하는 것은 아니다.

근거: [Make: Scenarios](https://www.make.com/en/integrations/scenario-service)

### 참여율 (ER) — 원본 235행

**정의:** 콘텐츠에 대한 좋아요·댓글·공유 등의 반응을, 정해진 기준 수치로 나눈 비율이다. 분모는 조회수·도달 수·노출 수·팔로워 수 등 측정 목적과 도구에 따라 달라지므로 계산 기준을 함께 표시해야 한다.

**예시:** 조회수 기준으로 좋아요 50개 + 댓글 20개 + 공유 30개 = 반응 100건, 조회수 2,000회라면 ER = 100 ÷ 2,000 × 100 = 5%다. 반응 100건이 서로 다른 100명을 뜻하지는 않는다.

근거: [Hootsuite: Engagement rate formulas](https://blog.hootsuite.com/calculate-engagement-rate/)

### 터미널 — 원본 237행

**정의:** 명령어를 입력하고 실행 결과를 글자로 확인할 수 있게 해주는 인터페이스다. 보통 터미널 안에서 셸을 실행하며, 셸이 명령을 해석한다. VS Code 전용 기능이 아니고 독립된 앱으로도 사용할 수 있다.

**예시:** Windows Terminal이나 VS Code의 통합 터미널에서 폴더 이동 명령을 입력하고 결과를 확인한다. 터미널은 명령을 주고받는 창, 셸은 명령을 해석하는 프로그램으로 구분해 이해할 수 있다.

근거: [Microsoft: Windows Terminal](https://learn.microsoft.com/en-us/windows/terminal/)

### 샌드박스 — 원본 238행

**정의:** 프로그램이나 AI 도구가 실행될 때 다른 시스템에 미치는 영향을 줄이도록 격리하거나 파일·네트워크 등의 접근 권한을 제한한 실행 환경이다. 단순한 행동 지침이 아니라 실행 범위를 기술적으로 통제하는 환경을 뜻한다.

**예시:** AI가 지정한 작업 폴더 안에서만 파일을 바꾸도록 제한할 수 있다. 어떤 파일·네트워크 접근을 허용하는지는 설정에 따라 다르며, 샌드박스라고 해서 모든 위험이 없어지는 것은 아니다.

근거: [Microsoft: Windows Sandbox](https://learn.microsoft.com/en-us/windows/security/threat-protection/windows-sandbox/windows-sandbox-overview)
