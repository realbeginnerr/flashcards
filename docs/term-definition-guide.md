## 1. 목적과 독자

이 문서는 UX/UI 디자인, 브랜딩, 마케팅, 개발, AI 등의 용어를 처음 배우는 사람을 위한 단어장 작성 기준이다. 목표는 사전식 정의를 외우게 하는 것이 아니라, 용어를 이해하고 실제 작업에서 알아볼 수 있게 만드는 것이다. 독자가 관련 전문 용어를 거의 모른다고 가정한다.

<a id="section-2"></a>

## 2. 핵심 작성 원칙

- **쉬운 일상 언어를 먼저 쓴다.** '사용자 행동을 시각화한 도구'보다 '사용자가 무엇을 했는지 순서대로 적어둔 자료'처럼 풀어 쓴다.
- **무엇인지뿐 아니라 왜, 언제 사용하는지 설명한다.** 독자가 자신의 작업에 연결해 이해하도록 한다.
- **짧음보다 이해를 우선한다.** 불필요한 말을 늘이지 않되, 설명이 부족해지도록 억지로 줄이지 않는다.
- **실제 행동과 상황을 보여준다.** 추상적인 장점 나열보다 '버튼을 누른 사람 수를 확인한다'처럼 구체적으로 쓴다.
- **말로 설명하듯 자연스럽게 쓴다.** 교과서식 정의, 과도한 전문 용어, 형식적인 문구를 피한다.
- **모든 용어에 공통으로 3가지 설명 요소를 포함한다.** 영어 원뜻, 업무에서 실제로 쓰는 말·상황, 이해를 돕는 구체적 비유 또는 사례를 구분해 제공한다. 각 요소의 길이와 비중은 용어에 맞게 조절한다.

<a id="section-3"></a>

## 3. 설명 구성 방법

최신 기준으로 영어 원뜻, 실무에서 실제로 쓰는 표현·상황, 비유 또는 구체적 사례의 3가지 요소를 모두 포함한다. 그 밖의 요소는 필요한 것만 골라 자연스럽게 연결한다. 순서는 이해하기 좋게 조정할 수 있다.

1. **쉬운 정의:** 무엇을 뜻하는지 한두 문장으로 설명한다.
2. **명칭 풀이:** 이름 때문에 오해할 수 있다면 왜 그런 이름인지 설명한다. 예: 고객여정지도는 일반적인 지리 지도가 아니다.
3. **사용 목적과 상황:** 어떤 문제를 해결하려고 쓰는지, 언제 필요한지 알려준다.
4. **사용 방법과 도구:** 종이, FigJam, 엑셀 등 실제로 가능한 작성·활용 방식을 소개한다.
5. **실무 팁:** 협업, 수정, 관리 등 초보자에게 유용한 조언을 덧붙인다.
6. **예시 또는 직접 확인 방법:** 일상적인 상황, 구체적 작업 사례, 검색어 중 가장 효과적인 방식을 선택한다.

<a id="section-4"></a>

## 4. 비유와 예시 선택 기준

- 일상에서 접하기 어려운 개념은 음식점, 창고, 레시피 등 익숙한 상황에 비유한다. 비유가 실제 기능과 다르면 어디까지 비유인지 구분한다.
- 직관적인 개념은 억지로 비유하지 않는다. 예: Amplitude는 방문자 수·버튼 클릭 등을 확인하는 사례로 설명할 수 있다.
- 예시는 **누가 → 무엇을 하고 → 어떤 결과를 얻는지** 보이도록 구체적으로 작성한다.
- 그림이나 화면을 봐야 이해가 빠른 용어는 '(예) 구글에서 CJM 검색해보기'처럼 실제 사례를 찾아보도록 안내해도 된다.
- 최신 기준: 각 용어에 원뜻, 업무에서 실제로 쓰는 예시, 비유 또는 구체적 사례를 구분해 넣는다. 단, 비유가 부자연스러우면 실제 작업 상황을 예시로 사용하고 억지 비유를 만들지 않는다.

<a id="section-5"></a>

## 5. 실무 정보와 학습 안내

- 초보자가 실제로 접할 프로그램, 메뉴, 파일, 작업 흐름을 언급한다.
- 하나의 도구만 정답인 것처럼 쓰지 않는다. 종이·FigJam·스프레드시트처럼 여러 방법이 가능하면 알려준다.
- AI와 협업할 가능성을 고려해, **AI가 읽고 재활용하기 쉬운 형태로 기록해 두면 좋다**는 식의 실무 조언을 필요할 때 제공한다. 특정 도구가 항상 AI에 더 적합하다고 단정하지 않는다.
- 단순 정의와 작성자의 실무 추천은 구분한다. 예: 'CJM은 여러 도구로 작성할 수 있다'는 설명이고, '협업을 위해 구조화된 파일로 관리하는 것이 좋다'는 조언이다.

<a id="section-6"></a>

## 6. 정확성 및 오해 방지

- **쉬운 설명이어도 틀리게 설명하지 않는다.** 서비스의 기능이나 측정 범위를 과장하지 않는다.
- **뜻이나 판단이 확실하지 않으면 반드시 사용자에게 확인한다.** 하나의 용어에 여러 뜻이 있어 어떤 뜻을 작성해야 할지 불분명한 경우, 설명 범위·사용 맥락·표현 방식 등과 관련해 질문이 생긴 경우, 그 밖에 사실이나 판단에 확신이 없는 경우에는 AI가 임의로 정하거나 추측해서 작성하지 않는다. 궁금한 내용을 먼저 사용자에게 질문하고, 답변과 확인을 받은 뒤 작성한다.
- 용어의 일반적인 의미와 특정 업계·팀의 관행을 구분한다.
- 해석이나 적용 범위가 여러 가지라면 짧게 밝힌다. 예: 고객여정지도는 사용 시작부터 종료까지 그릴 수도 있고, 제품을 알게 된 시점이나 구매 전후까지 포함할 수도 있다. 어느 범위가 더 흔한지는 근거 없이 단정하지 않는다.
- 비슷한 개념은 핵심 차이를 설명한다. 예: 컴포넌트(원본)와 인스턴스(연결된 복제본).
- 기술적 조건이 있는 기능은 조건을 밝힌다. 예: 분석 도구의 모든 행동 데이터가 자동 수집되는 것은 아니며 설정이 필요할 수 있다.
- 원문이 부정확하면 의미를 보존하려고 오류를 반복하지 말고, 수정이 필요한 부분을 확인하여 정확하게 쓴다.

<a id="section-7"></a>

## 7. 문체와 분량

- 기본 문체는 쉽고 친근한 설명체이며, 단어장 전체에서는 문장 끝을 '~다'로 통일한다.
- 한 문장에 낯선 개념을 여러 개 쌓지 않는다. 필요한 전문 용어는 처음 등장할 때 바로 풀어 쓴다.
- 불필요한 수식어와 반복을 줄인다. 실무 조언이나 예외 설명은 이해에 도움이 될 때만 넣는다.
- **분량은 요청별 조건을 우선한다.** 별도 제한이 없다면 이해에 필요한 만큼 작성한다. 사용자가 '공백 포함 100~300자'를 요청하면 제목·본문·예시 중 어떤 범위를 셀지 명확히 하고 그 범위를 준수한다. 이전 예시가 길다는 이유만으로 분량 제한이 자동 폐지되는 것은 아니다.

<a id="section-8"></a>

## 8. 작성 및 검토 절차

1. 용어의 뜻과 사용 맥락을 확인한다.
2. 초보자가 모를 표현을 쉬운 말로 바꾼다.
3. 사용 목적과 실제 상황을 한두 가지 떠올린다.
4. 이름에서 생길 오해, 비슷한 용어와의 차이, 적용 범위의 예외가 필요한지 확인한다.
5. 영어 원뜻, 실제 업무 발화·상황, 비유 또는 구체적 사례를 각각 포함하고, 필요하면 검색 안내도 덧붙인다.
6. 유용한 실무 팁이 있으면 추가하되 사실과 의견을 구분한다.
7. 마지막으로 정확성, 자연스러움, 중복, 요청한 글자 수를 확인한다.

## 9. 참고 예시

### GitHub — 비유 중심

웹/앱을 만드는 코드를 온라인에 보관하고 변경 기록을 확인하며 여러 사람이 함께 작업할 수 있도록 돕는 서비스다. 음식점의 레시피를 한곳에 보관하고 누가 언제 무엇을 바꿨는지 기록하는 공동 관리 공간에 비유할 수 있다. 다만 GitHub가 코드를 알아서 모두 정리해 주는 것은 아니다.

### Amplitude — 실제 사용 사례 중심

내 웹/앱에 방문한 사람들이 어떤 화면을 보고 어떤 버튼을 눌렀는지 분석하는 도구다. 예를 들어 회원가입 화면까지 온 사람 중 몇 명이 가입 버튼을 눌렀는지 확인해 어느 단계에서 사용자가 이탈하는지 살펴볼 수 있다. 필요한 행동은 미리 측정하도록 설정해야 할 수 있다.

### 고객여정지도(CJM) — 명칭 풀이·범위·실무 팁 중심

고객이 서비스를 이용하는 과정에서 어떤 행동을 하고 무엇을 생각하고 느끼는지 시간 순서대로 정리한 자료다. 일반적인 지리 지도는 아니지만 경험의 흐름을 펼쳐 보여주기 때문에 '지도'라고 부른다. 조사 목적에 따라 처음 서비스를 알게 된 순간부터 포함할 수도 있고 실제 사용 구간만 다룰 수도 있다. 종이, FigJam, 엑셀 등으로 만들 수 있다. 실제 형태가 궁금하다면 'CJM 예시'를 검색해 본다.

---

**AI에게 전달할 지시문 예시:** '첨부한 「초보자용 용어 뜻 작성 가이드」를 기준으로 다음 용어의 뜻을 다시 써줘. 기존 설명의 의미를 확인하되 오류는 바로잡고, 초보자가 이해할 수 있도록 구체적인 사례나 비유를 필요한 경우에만 추가해. 요청한 분량 제한을 지켜줘.'

## 10. 추가 수정 사례에서 발견한 작성 패턴

- **단어의 원래 뜻에서 시작한다.** 여러 분야에 쓰이는 말은 영어의 일반적인 의미를 먼저 풀어준다. 예: component는 '구성 요소·부품·성분'이라는 뜻이다.
- **설명 범위를 명시한다.** 같은 단어라도 분야에 따라 뜻이 다르므로 '다음 내용은 피그마 기준'처럼 어느 분야의 의미를 설명하는지 분명히 한다.
- **정의보다 상황을 길게 설명해도 된다.** 초보자가 실제 문제를 체감하도록 '컴포넌트 없이 버튼 100개를 고칠 때'와 '컴포넌트로 한 번에 바꿀 때'를 비교한다.
- **전문 용어 간 관계를 연결한다.** 원본 컴포넌트와 인스턴스처럼 함께 알아야 할 말을 같은 상황 안에서 소개한다.
- **분류를 먼저 보여준다.** 콘텐츠 디자인은 상세페이지, 카드뉴스, 광고 등 대표적인 결과물을 먼저 보여주면 범위가 빨리 이해된다.
- **작업의 의도도 설명한다.** 단순히 '시각적으로 표현하는 일'이라고 끝내지 않고 시선 집중, 정보 전달, 구매 유도 등 왜 제작하는지 알려준다. 다만 모든 콘텐츠 디자인의 목적이 판매인 것은 아니므로 '많은 상업용 작업에서는'처럼 범위를 제한한다.
- **추상적인 말을 이해 가능한 임시 정의로 바꾼다.** UX의 '경험'이 와닿지 않으면 '사용하면서 겪는 불편을 찾고 해결하는 일'처럼 처음 배우기 쉬운 관점으로 설명할 수 있다. 단, 이것이 UX 전체의 엄밀한 정의는 아님을 함께 밝혀야 한다.
- **핵심을 한 번 더 짧게 요약한다.** '더 짧게 말하면 문제 찾기, 해결하기'처럼 기억하기 쉬운 표현을 추가할 수 있다.
- **독자에게 직접 말하듯 쓴다.** '추상적이어서 잘 와닿지 않을 것이다', '우선 이렇게 기억해두자' 같은 설명을 허용한다. 다만 단정적인 사실과 교육용 단순화는 구분한다.

<a id="section-11"></a>

## 11. 상황에 따른 추천 설명 구조

고정된 형식이 아니라 아래 중 해당하는 방식을 고른다.

### A. 여러 분야에서 쓰는 용어 — 원뜻 → 적용 분야 → 기능 → 사례

예: 컴포넌트. 영어의 일반적 의미를 알려준 다음 피그마에서의 뜻으로 범위를 좁히고, 버튼 100개 사례로 장점을 체감하게 한다.

### B. 결과물이 눈에 보이는 용어 — 쉬운 정의 → 대표 종류 → 제작 목적

예: 콘텐츠 디자인. 상세페이지·카드뉴스·광고를 보여주고 각각의 정보를 전달하거나 행동을 유도하는 목적을 설명한다.

### C. 추상적인 용어 — 정확한 의미 → 어려운 이유 인정 → 임시 기억법 → 사례

예: UX. '사용자 경험'이라는 원뜻을 제시한 뒤, 초보자에게는 '불편 찾기와 해결하기'로 접근하도록 돕는다. 이 기억법이 UX의 모든 범위를 뜻하지는 않는다고 명시한다.

### D. 도구·방법론 — 실제 사용 장면 → 사용 전 문제 → 사용 후 변화

예: 컴포넌트와 GitHub. 기능 목록을 나열하기보다 왜 필요한지 문제 상황과 변화로 설명한다.

<a id="section-12"></a>

## 12. AI가 작성할 때의 최종 점검

- 이 단어의 일반적인 뜻과 지금 설명하는 업계의 뜻을 혼동하지 않았는가?
- 초보자가 뜻을 이해하는 데 필요한 사전 지식까지 제공했는가?
- '이 기능이 없을 때의 불편'과 '있을 때의 차이'를 보여주는 것이 더 효과적인가?
- 대표적인 작업물이나 예시를 구체적으로 제시했는가?
- 짧은 기억법을 썼다면 정확한 정의와 구분했는가?
- 영어 원뜻, 실제 업무 발화·상황, 비유 또는 구체적 사례를 모두 담았는가? 비유가 억지스럽지는 않은가?
- 문체가 설명하듯 자연스러우며, 길이 제한이 있다면 지켰는가?

<a id="section-13"></a>

## 13. 추가 참고 예시

### 컴포넌트 — 원뜻·분야 지정·전후 비교

컴포넌트는 원래 어떤 것의 '구성 요소'나 '부품'을 뜻한다. IT 분야에서 폭넓게 쓰이지만 여기서는 피그마를 기준으로 설명한다. 피그마에서는 버튼처럼 여러 곳에 반복해서 쓸 디자인의 원본을 컴포넌트로 만들 수 있다. 버튼 100개를 일일이 수정하는 대신 원본 하나를 바꾸면 연결된 복제본에도 변경 사항을 반영할 수 있다. 이 복제본을 '인스턴스'라고 부른다. 다만 인스턴스에 별도로 설정한 속성은 원본 변경이 그대로 적용되지 않을 수 있다.

### 콘텐츠 디자인 — 대표 결과물·목적 중심

사람에게 전달할 정보를 보기 좋고 이해하기 쉽게 시각적으로 구성하는 디자인 작업이다. 상세페이지, SNS 카드뉴스, 광고 이미지 등이 대표적이다. 화장품 상세페이지라면 제품 사진과 설명을 배치해 장점을 쉽게 파악하게 만들 수 있다. 상업용 콘텐츠는 시선을 끌고 구매 같은 행동을 유도하려는 목적이 많지만, 정보 전달 자체가 목적인 콘텐츠도 있다.

### UX — 정확한 정의와 입문용 기억법 구분

UX는 '사용자 경험'이라는 뜻이다. 경험이라는 말이 추상적이라면 처음에는 '사용자가 제품을 쓰면서 겪는 불편을 찾고 해결하는 일'이라고 기억해도 좋다. 더 짧게 말하면 '문제 찾기, 해결하기'다. 예를 들어 배달 앱에서 주문 과정이 복잡해 고객이 포기한다면 그 이유를 찾고 개선하는 작업이다. 다만 UX에는 편리함뿐 아니라 감정, 기대, 만족 등 더 넓은 경험도 포함된다.

## 14. 추가 분석: 플랫폼·해상도·키비주얼과 개념 구분

- **일상적인 원뜻에서 전문 분야의 뜻으로 연결한다.** 플랫폼은 본래 평평한 구조물·승강장을 뜻한다. IT에서는 다른 사람이 활동하거나 서비스를 구축할 수 있게 제공하는 기반이라는 뜻으로 확장된다. 원뜻과 전문 뜻의 연결고리를 설명하되, 단순한 어원 비유를 엄밀한 정의로 착각하지 않게 한다.
- **숫자와 조건을 제시하면 이해가 쉬운 개념은 실제 수치로 비교한다.** 동일한 27인치 모니터의 FHD(1920×1080)와 4K(3840×2160)를 비교하면 4K의 전체 픽셀 수는 4배, 픽셀 한 변의 물리적 크기는 약 절반이다. 화면 크기가 같다는 조건을 밝혀야 한다.
- **가까운 개념을 구분한다.** 이미지 해상도는 흔히 가로×세로 픽셀 수를 뜻하고, 화면의 픽셀 밀도는 PPI로 표현한다. 해상도·픽셀 밀도·사진의 실제 선명도를 동일시하지 않는다.
- **작업의 일반적인 흐름과 필수 절차를 구분한다.** 무드보드가 키비주얼 제작에 도움이 되지만, 이미 브랜드 가이드와 콘셉트가 충분히 정해져 있다면 무드보드를 새로 만들지 않을 수 있다. '주로 이렇게 한다'와 '반드시 이렇게 해야 한다'는 다르다.
- **비슷한 말의 관계를 설명할 때 지나친 단순화를 피한다.** UX는 경험 자체를 뜻하고 UX 디자인은 경험을 설계·개선하는 작업이다. UI는 사용자가 시스템과 상호작용하는 접점으로, 단순히 화면의 색상·모양만을 뜻하지 않는다.
- **플랫폼 같은 포괄적인 단어는 대표적인 유형을 나눈다.** 쿠팡처럼 판매자와 구매자가 만나는 거래 플랫폼과 Shopify처럼 쇼핑몰 구축·운영 기능을 제공하는 플랫폼은 모두 전자상거래 플랫폼으로 불릴 수 있지만 역할이 다르다.

<a id="section-15"></a>

## 15. 최종 출력 형식

- 사용자가 '단어 / 뜻'과 탭 구분을 요청하면 한 줄에 한 단어씩 작성하고, 단어와 뜻 사이에 탭 문자 하나를 넣는다.
- 복사·붙여넣기가 목적이라면 결과를 코드 블록에 담는다. 코드 블록 안에는 제목 기호, 번호, 불릿, 굵게 표시하는 마크다운 문법을 넣지 않는다.
- 뜻에 여러 문장이 들어가더라도 하나의 셀에 들어가도록 줄바꿈 없이 한 줄로 쓴다. '(예)' 표시는 같은 줄에 이어 쓸 수 있다.
- 열 이름이 요청되지 않으면 헤더를 임의로 추가하지 않는다. 원본 단어의 순서와 표기를 유지한다.
- 문체는 '~다'로 통일하되, 자연스러운 교육용 표현과 질문형 사례는 허용한다.

## 16. 최신 수정 패턴: 압축된 조작 예시와 3가지 설명 요소

### A. 사용자 수정에서 확인된 패턴

1. **예시는 실제 조작을 한 문장으로 보여준다.** 설정 패널에 항목이 나타난다는 설명, W가 Width의 첫 글자라는 해설, 픽셀 단위의 예외 조건 등을 장황하게 반복하기보다, 사용자가 어디를 클릭하고 무엇을 입력하면 어떤 결과가 나오는지 직접 설명한다.
   - 수정 전: '버튼을 선택하면 오른쪽 설정 패널에 W라는 항목이 나타난다. W는 Width의 첫 글자로 ... 여기에 200을 입력하면 ...'
   - 수정 후: '(예) 피그마에서 버튼을 선택하고 오른쪽 설정 패널에 있는 W라고 적힌 입력창에 200을 입력하면 버튼의 너비가 200픽셀이 된다.'
   - 높이도 동일한 구조로 작성한다: '(예) 피그마에서 버튼을 선택하고 오른쪽 설정 패널에 있는 H라고 적힌 입력창에 48을 입력하면 버튼의 높이가 48픽셀이 된다.'
2. **정의나 예시에서 이미 알 수 있는 내용을 다시 요약하지 않는다.** 'Width는 보통 W로 줄여 표시하므로 기억해두는 것이 좋다', 'Width(W)는 가로 크기, Height(H)는 세로 크기라는 차이를 기억하면 된다'처럼 학습 효과가 적은 반복 문장은 삭제한다.
3. **현업에서 실제로 듣는 문장을 추가한다.** 단어가 회의, 피드백, 업무 지시에서 어떤 표현과 함께 쓰이는지 보여준다. 예: '기획서 보시고 화면 레이아웃만 먼저 잡아보실래요? 디테일 작업은 아직 하지 마시고요.' '레이아웃 잡다'의 의미를 이어서 풀어 설명한다.
4. **뜻을 작업 단위로 구체화한다.** '레이아웃=배치'에서 끝내지 않고 사진·글자·버튼의 위치, 크기, 간격, 정렬, 여백을 정하는 일까지 연결한다.

### B. 앞으로 모든 용어에 포함할 3가지 요소 (최신 필수 기준)

1. **영어 단어의 원래 뜻:** 영어 표기와 일반적인 의미를 설명하고, 디자인·개발·마케팅 등 해당 분야의 의미로 연결한다. 약어라면 풀어 쓴 이름과 각 부분의 의미를 설명한다. 원뜻이 불분명하거나 한국어 표현인 경우에는 억지로 어원을 만들어내지 말고 명칭의 뜻과 유래를 확인 가능한 범위에서 설명한다.
2. **업무 관련 예시:** 회의·기획서·디자인 피드백·업무 요청 등에서 그 단어가 실제로 어떤 문장으로 쓰이는지 직접 인용 형태로 보여주고, 그 말이 구체적으로 어떤 일을 하라는 뜻인지 설명한다. 현실적인 업계 표현을 사용하되 업계 전체가 반드시 같은 말을 쓴다고 단정하지 않는다.

### 업무 관련 예시 작성 원칙

1. **실제 업무 상황을 구체적으로 설정한다.** 단순히 용어가 들어간 문장을 만드는 것이 아니라, 실무자가 어떤 업무를 수행하는 중에 해당 용어를 사용하는지 보여준다.

2. **업무의 배경과 목적을 포함한다.** 필요한 경우 프로젝트의 목적, 진행 중인 작업, 발견한 문제 등을 설명해 해당 발언이 나온 맥락을 이해할 수 있도록 한다.

3. **실제 직장인의 자연스러운 발화로 작성한다.** 회의, 업무 보고, 동료와의 대화, 작업 요청 등에서 실제로 사용할 법한 표현을 사용한다. 교과서처럼 짧고 인위적인 예문은 피한다.

4. **업무의 흐름이 드러나도록 작성한다.** 필요하다면 '업무 목적 → 수행한 활동 → 발견한 사실 → 판단 또는 요청' 순서로 상황을 구성한다. 모든 단계를 반드시 포함할 필요는 없다.

5. **구체성을 위해 문장 길이를 제한하지 않는다.** 짧은 문장으로도 자연스럽게 설명할 수 있다면 간결하게 작성하되, 업무 맥락을 전달하기 위해 필요하다면 여러 문장을 사용한다.

6. **용어를 억지로 사용하지 않는다.** 실제 업무에서 해당 용어를 사용하는 것이 자연스러운 상황을 선택한다. 예시 자체가 용어의 의미와 사용 목적을 이해하는 데 도움이 되어야 한다.
7. **비유 예시 또는 구체적인 상황 예시:** 초보자가 장면을 떠올릴 수 있도록 익숙한 비유나 실무 상황을 제시한다. 비유가 부자연스러우면 쇼핑몰 상세페이지, 피그마 버튼 설정 등 실제 작업 사례로 대체한다. '무엇을 어디에 어떻게 배치/설정하고 결과가 어떻게 달라지는지'를 보여준다.

세 요소는 **내용상 구분**하되, 사용자가 요청하지 않으면 매번 딱딱한 소제목을 붙일 필요는 없다. 설명의 중복을 피하고 문장 흐름을 자연스럽게 유지한다. 기존 문서의 '예시는 필수가 아니다', '모든 용어에 같은 틀을 강요하지 않는다'라는 지침보다 이 최신 필수 기준을 우선한다.

### C. 레이아웃 작성 기준 예시

- **원뜻:** Layout은 '배치'라는 뜻이다. 디자인에서는 화면의 구조나 요소의 배치를 가리킨다.
- **업무 관련 예시:** '기획서 보시고 화면 레이아웃만 먼저 잡아보실래요? 디테일 작업은 아직 하지 마시고요.' 여기서 '레이아웃을 잡다'는 요소의 위치, 크기, 간격을 먼저 정하라는 뜻이다.
- **구체적 상황 예시:** 쇼핑몰 상세페이지에서 제품 사진, 상품 설명, 구매 버튼의 위치와 간격을 정하는 작업이다. 요소의 정렬과 여백, 관련 정보의 묶음도 고려한다.

### D. 최종 점검 추가

- 영어 원뜻 / 업무에서의 실제 발화 / 비유·상황 예시의 세 요소가 모두 있는가?
- 업무 발화가 단순한 용어 정의의 반복이 아니라 실제 회의나 요청에서 들을 법한 말인가?
- 도구 사용 예시가 '선택 → 입력·조작 → 결과'로 간결하게 이어지는가?
- 앞에서 이미 설명한 내용을 '기억해두는 것이 좋다' 등으로 반복하지 않았는가?
